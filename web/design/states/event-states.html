Event states

Six values, from events/event.go:19. The set is closed and validated server-side — rescued and ignored are explicitly rejected, so the UI never needs a fallback branch for a seventh.

The six

ok The task ran and changed nothing. The quiet majority. quiet changed Something on a real machine was modified. The answer to the only question that matters after a run. loud failed The task ran on the host and failed. A problem in the play. loud unreachable The host was never reached. A problem in the network or the inventory. loud skipped A when: said no. Expected, and rarely interesting. quiet unknown Kept on purpose. Dashed border: it reads as an admission, not as a result. admission

failed ≠ unreachable

failed
We reached the machine. It did what we asked and the task did not succeed. Go read the playbook.
unreachable
We never got there at all. SSH, the key, the address, the host key. Go read the inventory.

Two different files to open, so two clearly different colours — red and magenta, never two shades of the same hue. This is the single most common misreading in an Ansible summary, and colour is what prevents it.

Why changed gets full weight. It is tempting to treat ok and changed as one calm family and reserve colour for failure. That would be backwards: this product exists to answer what had already changed when a run was cut short mid-flight — the README says so, and it is why events are persisted as they happen rather than buffered. GET /runs?changed_min= exists for the same reason. Muting changed would hide the field the whole system is built to record.
